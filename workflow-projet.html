Caries Detection Assistant — Workflow du projet

Le projet. Un outil qui, à partir d'une radio panoramique dentaire, détecte les caries (Deep Learning) puis, avec un assistant (RAG), explique le résultat et propose les traitements avec sources. Objectif : sur une radio, des caries sont manquées ou interprétées différemment selon le praticien — l'outil sert de second lecteur. Les deux briques (détection + assistant) servent le même cas d'usage et sont réellement intégrées. Contrainte machine : pas de GPU + proxy SSL → tout ce qui est lourd (entraînement, tuning) se fait en ligne (Colab GPU), le reste (EDA, RAG, démo, API) tourne en local.

Au départ — cadrage

  1. On fixe le sujet en respectant la règle (ML ou DL) + (Agent ou RAG) : ici détection de caries (DL) + assistant de traitement (RAG). Pourquoi ce sujet : sur radio, l'humain rate des caries et n'est pas constant → l'IA a une vraie valeur de second lecteur (contrairement à un problème que réglerait un simple seuil).
  2. On cherche d'abord un dataset réel, sinon rien n'est possible : DC1000 (~1000 radios + masques annotés par des dentistes). Il est stocké hors Git (1,1 Go) et téléchargé depuis sa source ; le repo ne garde que le code.
  3. On regarde l'état de la machine : pas de GPU, un proxy SSL qui intercepte le réseau, et transformers cassé. Conséquence : l'entraînement se fera en ligne, et le RAG utilisera Gemini (embeddings + génération) plutôt que des modèles locaux lourds.

Phase 1 — Données & EDA Local

  1. src/data/eda.py explore le dataset : nombre d'images, tailles, exemples radio + masque, et la part de pixels « carie ». Les sorties vont dans reports/ (stats + figures).
  2. Découverte structurante Les caries représentent ≈ 1 % des pixels : très déséquilibré. Pourquoi ça compte : l'accuracy serait trompeuse → on choisit la métrique Dice/IoU et une perte Dice + BCE (dans metrics.py) qui résiste au déséquilibre.

Phase 2 — Modèle de détection (U-Net) En ligne

  1. Le code est en scripts .py (pas tout dans un notebook) pour un pipeline reproductible : unet.py (architecture), dataset.py (chargement + split), train.py (entraînement + suivi MLflow), predict.py (inférence). Pourquoi U-Net : on veut localiser et mesurer chaque carie au pixel (segmentation), pas seulement dire « carie / pas carie ».
  2. On prévoit une baseline (seuillage d'Otsu dans evaluate.py) pour prouver que le Deep Learning apporte réellement quelque chose.
  3. L'entraînement se lance en ligne via notebooks/entrainement_colab.ipynb : il clone le repo, télécharge DC1000, entraîne sur GPU, puis on récupère models/unet_caries.pth.
  4. Piège Colab Après un git pull, il faut redémarrer la session (Python garde l'ancien code en cache) et vérifier Device : cuda (sinon l'entraînement part sur CPU, très lent).

Phase 3 — Évaluation & analyse d'erreurs En ligne

  1. Piège majeur — décalage de distribution Au début, on évaluait sur les panoramiques pleine résolution alors que le modèle s'entraîne sur des imagettes 384×384 : deux distributions différentes → Dice ≈ 0, chiffre trompeur. Correction : un découpage train / val / test de la même distribution (dans dataset.py), le test jamais vu à l'entraînement.
  2. Résultat honnête : U-Net Dice ≈ 0,42-0,46 contre baseline Otsu ≈ 0,02 (≈ 21× mieux). Écrit dans reports/metrics_test.json.
  3. src/model/error_analysis.py détaille les erreurs : Dice par image, pires et meilleurs cas, faux positifs / faux négatifs. On constate que le modèle rate un peu plus de caries qu'il n'en invente — utile pour les pistes d'amélioration.

Phase 4 — Assistant RAG Local

  1. On rédige un corpus sourcé dans rag_corpus/ (fiches : définition/stades des caries, traitements, dévitalisation vs extraction, radio panoramique).
  2. src/rag/ingest.py découpe ces fiches en chunks, calcule les embeddings Gemini et construit l'index Chroma (chroma_caries/, régénérable, hors Git).
  3. src/rag/assistant.py récupère les passages pertinents et génère une réponse sourcée. Paramètres LLM explicites : temperature=0, top_p=0.9, max_output_tokens=1024, prompt système « réponds uniquement d'après le contexte ». Pourquoi : on veut de la fidélité, pas de la créativité qui inventerait des faits médicaux.
  4. src/rag/evaluate_rag.py mesure la qualité : pertinence du retrieval (hit@k) et comparaison LLM seul vs LLM + RAG → montre que sans sources, le LLM répond de façon moins fondée.
  5. Piège SSL Le proxy bloque l'API Google en local → flag CARIES_INSECURE_SSL=1 dans .env (jamais commité, géré par src/rag/_ssl.py). En ligne, on ne l'active pas.

Phase 5 — Intégration & démo Local

  1. Le cœur du fil rouge On branche les deux blocs : la sortie de la détection (nombre de zones, surface) devient le contexte de l'assistant. Les deux ne sont pas juxtaposés, ils s'enchaînent dans un même flux.
  2. app/app.py — démo Streamlit : on charge une radio → caries surlignées + réponse sourcée. Le cas « modèle absent » est géré proprement.
  3. app/api.py — API FastAPI : /predict (détection), /assistant (réponse), /health.

Phase 6 — Hyperparamètres & MLOps En ligne

  1. src/model/tune.py compare plusieurs configurations (lr, filtres, taille), loguées dans MLflow, et retient la meilleure (reports/hyperparam_search.json).
  2. Piège corrigé Le tuning ne doit pas écraser le modèle de production : une config de taille différente casserait l'inférence en 256. On garde le modèle 256 comme référence.
  3. Bonus MLOps : MLflow (suivi des runs), Docker (Dockerfile pour l'API), données et modèles versionnés hors Git.

Phase 7 — Livrables

  1. Le cahier des charges, le dépôt GitHub (code, README, notebooks, requirements, Dockerfile, rapports), la démo exécutable et la présentation 10-12 slides.

Fil conducteur : une seule vraie dépendance forte — les données, puis le modèle entraîné ; tout le reste (RAG, démo, API, rapports) s'articule autour. La contrainte machine impose la frontière local / en ligne, mais ne bloque aucune étape.

Tout ce que contient le dépôt, et à quoi sert chaque fichier. Les données, modèles et secrets sont hors Git.

Racine

  • README.md — objectif métier, stack, données (source, licence, limites), utilisation, liste des évaluations.
  • requirements.txt — dépendances Python.
  • Dockerfile — image de l'API FastAPI (bonus MLOps).
  • .env.example — modèle de configuration ; le vrai .env (clé Gemini + flag SSL) est hors Git.
  • workflow-projet.html — ce document.

Code — src/

  • src/config.py — chemins et hyperparamètres centralisés (une seule source de vérité).
  • src/data/dataset.py — charge une radio + son masque, et fait le découpage train/val/test (déterministe, sans fuite).
  • src/data/eda.py — analyse exploratoire (stats + figures).
  • src/model/unet.py — l'architecture U-Net.
  • src/model/metrics.py — la perte Dice+BCE (adaptée au déséquilibre) et les métriques Dice/IoU.
  • src/model/train.py — l'entraînement (sur GPU en ligne), avec suivi MLflow et sauvegarde du meilleur modèle.
  • src/model/evaluate.py — évalue le U-Net sur le test et le compare à la baseline Otsu.
  • src/model/error_analysis.py — analyse d'erreurs : Dice par image, pires/meilleurs cas, faux positifs/négatifs.
  • src/model/tune.py — recherche d'hyperparamètres (compare plusieurs configs, log MLflow).
  • src/model/predict.py — inférence : d'une radio vers un masque + stats. Utilisé par la démo et l'API.
  • src/rag/ingest.py — construit l'index vectoriel Chroma à partir du corpus.
  • src/rag/embeddings.py — fournit les embeddings Gemini (pas de dépendance locale lourde).
  • src/rag/assistant.py — retrieval + génération sourcée ; contient les paramètres LLM explicites.
  • src/rag/evaluate_rag.py — évalue le RAG (hit@k + LLM seul vs LLM+RAG).
  • src/rag/_ssl.py — contournement du proxy SSL en local (activé par un flag, jamais en ligne).

Contenu & notebooks

  • rag_corpus/*.md — les fiches sources de l'assistant (définition/stades, traitements, dévitalisation vs extraction, radio).
  • notebooks/entrainement_colab.ipynb — entraînement + tuning + analyse d'erreurs sur GPU en ligne.
  • notebooks/eda.ipynb — exploration des données (le PDF attend un/des notebook(s)).

Application

  • app/app.py — démo Streamlit : radio → caries surlignées + assistant.
  • app/api.py — API FastAPI (/predict, /assistant, /health).

Rapports — reports/ (les preuves)

  • eda_stats.json, eda_*.png — sorties de l'EDA (dont le déséquilibre).
  • metrics_test.json — Dice/IoU du U-Net vs baseline.
  • error_analysis.json, error_*.png — analyse d'erreurs.
  • hyperparam_search.json — comparaison des configurations.
  • rag_eval.json, rag_eval_comparaison.md — évaluation du RAG.

Hors Git non versionné

  • data/ — dataset DC1000 (~1,1 Go), téléchargé depuis la source.
  • models/unet_caries.pth — le modèle entraîné (récupéré depuis Colab).
  • chroma_caries/ — l'index vectoriel, régénéré par ingest.py.
  • .env — la clé Gemini et le flag SSL local.
